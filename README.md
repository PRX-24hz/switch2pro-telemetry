## 这是什么

不写设备的前提下，把 Switch 2 Pro 手柄 `0x05` 报告能挖的信息挖到底。**结论是：这一帧基本够用了。**

- **能量化的**：链路时钟（含 23.86 分钟回绕常数）、6 个充电状态值、完整充电周期时序、
  摇杆实际量程、震动对功耗的影响、**内置六轴 IMU 的量程 / 轴向 / 零偏**
- **证伪的**：社区流传的三段式充电状态机、用锂电曲线换算百分比、
  「`0x05` 只有按键摇杆电量」、「上电即流、无需握手」
- **仍然做不到的**：真实电量百分比（该字段不是电压）、`0x09` 的 0–9 档位、NFC、SPI 校准块

## 八条核心事实

| # | 事实 | 强度 |
|---|---|---|
| 1 | `0x05` 报告 **64 字节、250 Hz（4 ms）**，一帧内含按键 / 摇杆 / 电量 / 微秒时间戳 / 温度 / **六轴 IMU** | 硬 |
| 2 | **打开设备 ≠ 收到数据**：未激活时 **0 帧**；被主机激活后**直接 250 Hz**，无爬坡；激活后关掉发起软件，流仍持续 | 硬（热插拔 + 进程对照） |
| 3 | 时钟 = **32 位毫秒计数**，在 **1,431,655.765 ms** 回绕（= 2³² ticks @ 3 MHz）；时基实测 **+10 ppm** | **最硬**（10+ 次预测命中，偏差 ≤12 ms） |
| 4 | 状态字节是**位域**：b5=电源在位，b2=有充电电流，b4:b3 **不是**单调阶段索引 | 中（6 个取值全覆盖，阶段假说被自身数据反驳） |
| 5 | 充电结束后并非静止：**8.8 小时的「2.9 Hz 斩波维持」→ 10 分钟真充 → 完成** | 硬（整夜连续 9 小时记录） |
| 6 | 读数**不是电压**（满电仅 ≈3670–3728），且跟随斩波摆动 **±10、滞后 40–60 ms** | 硬（15,001 帧滞后实验） |
| 7 | **摇杆只用掉约 86–88% 的 12 bit 量程**（半径 1,765/1,810，裸 HID 推到底也到不了 0/4095）。**但 Steam/SDL 会归一化到满量程**，所以这条只影响直接解原始字节的人 | 硬（7,750 帧极限行程 + Steam 三点对照） |
| 8 | 尾部 12 字节是**完整六轴 IMU**：加速度 **±8 g**、陀螺 **±2000 dps**，六面标定后三轴一致到 **0.14%** | 硬（六面 + 角速度积分双路径，且与上游标称值独立吻合） |

> 第 2 条是 2026-10-25 才确认的，它推翻了我们自己早期写的「上电即流」。
> 第 8 条把「要 IMU 必须走 `0x09`」这个前提也推翻了：**只读轮询 `0x05` 就能拿到 IMU。**

## 一句话模型

```
插上 → 0x34 大电流充电 ──→ 0x3C(10s) ──→ 0x20 静止/缓慢掉电（数小时）
                                              │
                                              ↓ 约 8.8 小时
                                    0x00/0x24 斩波维持（2.9 Hz，`0x00` 断开占比 →90%）
                                              │
                                    ┌─────────┘
                                    ↓ 7 分钟「翻腾期」
                          0x24 → 0x34(4ms) → 0x2C(440ms) 循环 38 次
                                    ↓
                          0x34 满功率再充约 10 分钟 → 0x3C → 0x20
```

**红灯只跟随 `0x34`**。`0x20` 与斩波维持期间都是**熄灭**的——所以红灯不表示"是否接着电源"。

## 已作废的结论（如果你看过旧版）

| 旧说法 | 现状 |
|---|---|
| `0x20` 不存在 / 二手文档错了 | **错**。`0x20` = 充电完成，已多次实测 |
| `0x20` 是吸收态，只能放电退出 | **错**。拔插即可退出 |
| `0x2C` = 插上初期握手 | **错**。插入序列里它排第三 |
| b4:b3 是单调的阶段进度 | **不成立**。观测到 `0→2→1→2` |
| 读数在 `0x00` 时系统性偏低 20 | **不成立**。是锯齿，符号随采样落点翻转 |
| 斩波会收敛到 100% 并转 `0x20` | **方向错**。实际是反转成满功率再充 |
| `0x00` 占空比 ≥75% 即"已满" | **降级**。它度量"不充电的时间占比"，不等价于满 |

每条推翻的证据与当时为何会错，见 [`docs/daylog-2026-10-24.md`](docs/daylog-2026-10-24.md)。

## 这些结论对谁有用

| 你的场景 | 价值 |
|---|---|
| 写长跑型 HID 读取器（驱动、悬浮窗、手柄测试、延迟测量） | **必须有**：不处理回绕，每 23.86 分钟误报约 **357,900 帧丢失** |
| 写手柄输入映射 / 死区 / 灵敏度曲线 | **必须有**：按 4,095 归一化时推到底只有 **0.86**，表现为"永远推不满、转视角慢半拍" |
| 做体感 / 姿态 / 晃动检测，且不想装驱动 | **能落地**：`0x05` 自带六轴（±8 g / ±2000 dps），只读轮询即可，**不需要 `0x09`** |
| 做电量显示但**不能/不愿写设备** | **能落地**：四态 + 原始读数；拿不到真实百分比 |
| 已决定走 `iface1` 写命令拿 `0x09` | **价值低**：`0x09` 直接给 0–9 档位，只需容忍 `0x3C` 瞬态 |
| 只想看电量百分比 | **做不到**：字段不是毫伏，且缺低电端锚点 |
| 逆向方法论 / 想继续挖 | **高**：分层与开放问题就是路线图 |

> 前提：**这里没有"更好"，只有"不能写设备时还能拿到什么"。**

## 快速开始

```bash
pip install hidapi

# 0. 前置：设备必须已被"激活"一次，否则读到的是 0 帧（见 protocol §1.5）
#    最快办法：打开一次 Steam（停在登录页就够），等它识别到手柄，然后完全退出
#    Steam 退出后数据不会中断——激活是一次性开关
python tools/probe_env.py 6                # 自检：只有 0x05、250 Hz、az ≈ +1 g

# 1. 抓 4 帧，看字段
python tools/probe_switch_pro.py

# 2. 连续采样并落 CSV（每秒一行）
python tools/probe_switch_pro.py --watch 600 --csv sw2.csv

# 3. IMU：六面标定 + 分段 + 陀螺积分
python tools/imu_calib.py 100 --csv imu_calib.csv
python tools/imu_segments.py  imu_calib.csv    # 切出静止平台与运动事件
python tools/imu_gyro_fit.py  imu_calib.csv    # 角速度积分 → 量程与符号

# 4. 让另一台设备跑一遍复现（判定 4 条假设，输出 JSON）
python tools/repro_capture.py --minutes 30 --fw "<固件版本>"

# 5. 自证只读
python tools/audit_readonly.py
```

工具会向上查找本地 `_pylibs` 兜底，但仓库**不随附预编译二进制**。

## 只读承诺

不写设备的理由不是洁癖，是**失败模式不可逆**：

| 若写入 | 后果 |
|---|---|
| SPI 命令 | 误写摇杆校准区 → 永久漂移 |
| 固件/OTA | 最坏变砖 |
| `0x09` 初始化 | 改报告模式，并与 Steam/SDL 抢同一设备 |
| 震动/LED 输出 | 覆盖用户当前状态 |

```bash
python tools/audit_readonly.py
# 只读区：21 个 Python 文件
# ── 写入区（隔离，知悉即可）──
#   tools\write\replay_activation.py  → 5 处写调用
#   tools\write\send_activation.py    → 1 处写调用
#   tools\write\send_ctrl.py          → 8 处写调用
# [PASS] 只读区未发现任何写设备调用。
# [NOTE] 另有 14 处写调用位于 tools/write/，已隔离，不计入本判定。
# 只读区实际使用的接口：h.close, h.open_path, h.read, hid.device, hid.enumerate
```

审计脚本**分区判定**：只读区出现写调用即 FAIL；`tools/write/` 只登记不判定。这样「只读」是一条
可执行的检查，而不是一句自我声明。

**边界要说清，分三层**：

| 层 | 谁在写 | 说明 |
|---|---|---|
| 本仓库 `tools/` | 不写 | 全部为只读探针，审计可证 |
| 本仓库 `tools/write/` | **写** | 3 个实验脚本，尝试自己激活手柄，全部失败，隔离存放 |
| Steam 客户端 | **写** | 激活由它完成（**停在登录界面即可，不必登录**）；实测开启 Steam Input 后玩家指示灯也会被改写 |

所以准确表述是：**本仓库的数据是只读得来的，但「设备被激活」这一步不是我们做的。**
用户看到指示灯变化时，无法分辨是哪个软件做的。

## 状态与局限

- **单台设备、单一固件**（港版 `BBE-008`，版本号未记录）。所有"跨设备恒定"的结论都还没验证。
- **读数的量纲未定**：只证明了"不是电压"，没有证明"是什么"。需要外部电压参照。
- **摇杆 86% 可能是个体差异**：应理解为"必须标定，不要假设满量程"，而非型号规格。
- **3 MHz 只是数值拟合**：没有固件证据；严格说只确定了 `模数/分频` 的比值。
- **数据采自"已被激活"的设备**：激活由 **Steam 客户端**完成（停在登录界面即可，不需登录，关掉后流不中断）；
  本仓库没有实现激活（见 [`tools/write/`](tools/write/)）。拔线重插后退回未激活状态。
- **IMU 参数来自手测摆放**：没有夹具，各姿态残余倾角 0.03°–3°；陀螺只标到 ±2000 dps 这一档，
  **未做饱和测试**；安装偏角无法与摆放误差分离。
- **未触及**：命令-响应协议、SPI 校准区、固件 OTA（均需写设备）。

- **n=1**：单台设备、单一固件（版本待填）。所有"跨设备恒定"的结论都未验证；
- **读数的量纲未定**：只证明了"不是电压"，没证明"是什么"；
- **摇杆 86% 可能是个体差异**：应理解为"必须标定"，不是型号规格；
- **3 MHz 只是数值拟合**：严格说只确定了 `模数/分频` 的比值；
- **未读固件、未读 SPI、未走 `0x09`**：这些都需写设备，超出只读红线。

**欢迎协助**：如果你能提供第二台设备复现（30 分钟即可，见 [`REPRODUCE.md`](REPRODUCE.md)）、
一个 USB 功率计的数据、一份不同固件版本的样本，或对文档/算法有任何改进建议——
请开 issue 或直接提 PR。这正是把 n=1 升级为"型号级事实"的唯一途径。
