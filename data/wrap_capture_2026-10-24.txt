# 1432s 硬件时钟回绕 · 实机捕获记录（多轮命中 + 1 次非回绕重置）

设备：Nintendo Switch 2 Pro Controller (057E:2069)，USB 直连（拓展坞），**纯只读**
工具：tools/wrap_watch.py（250Hz 读 0x05 报告，仅跟踪 clock 字段）
时间：2026-10-24 08:27–09:00 GMT+8

## 假设（事前提出，可证伪）

若 clock 是「32 位 3 MHz tick 计数器，上报前 /3000 折算为毫秒」，则每次回绕必发生在

    2^32 / 3e6 * 1000 = 1,431,655.765 ms

且回绕后归零（而非取模到残差）。

## 两次独立捕获

| 捕获 | 时刻 | 回绕前最后读数 | 偏差 vs 理论 | 回绕后首帧 |
|---|---|---|---|---|
| 第 4 次 | 08:35 前后 | 1,431,650 ms | **-5.8 ms**（-4.0 ppm） | 0 ms |
| 第 5 次 | 08:59:36 | 1,431,652 ms | **-3.8 ms**（-2.7 ppm） | 1 ms |
| 第 6 次 | 09:33:17 | （心跳粒度，见下） | **双向推算差 6 ms** | 17,057 ms |

两次偏差都 <2 个采样间隔（250Hz = 4 ms/帧）。第 5 次的 `1,431,652` 恰好是
**低于 1,431,655.765 的最大 4 的倍数**（`1431652 = 4 × 357913`）——即该相位下
4ms 步进计数器**理论上的最后一个可读值**，属于完全命中而非近似。

第 4 次的 `1,431,650 % 4 = 2`，相位与第 5 次不同（两次链路建立时刻不同，相位随链路起始偏移）。

## 结论

假设成立，且**连续两次预测命中**，排除"偶然撞上"的可能：

- 回绕周期 = 1,431.6558 s = **23.8609 分钟**（由 2^32 ticks @ 3MHz 决定）
- 反推 tick 频率 = 2^32 / 1.431655765 s = **3.0000 MHz**
- 回绕后计数器**归零**，不是取模
- 因此回绕点可**预测**，不必被动检测；但实现仍应以 `clock <= prevClock` 兜底

## 第 6 次（顺手捕获，单日志双向互校）

监听状态字节期间恰好跨越回绕点，日志里前后两个心跳形成**两条独立推算**：

```
09:33:04  clock = 1,418,707 ms   →  距理论点 12,948.8ms  →  推算回绕 = 09:33:16.948
09:33:34  clock =    17,057 ms   ←  倒推         17,057ms  →  推算回绕 = 09:33:16.943
                                                        两法差 = 6 ms
```

这一次没有 250Hz 密集采样，却用「前一帧外推 + 后一帧回推」得到互相一致的 6ms，
说明该常数的稳定性不依赖采样密度，是真实的硬件量。

三次捕获汇总：偏差 -5.8ms / -3.8ms / 双向 6ms，均在 1~2 个采样间隔内。


## 第 7 次（12:44）—— 反例：归零但不是回绕

```
09:14 起监听，12:35:06 最后一条心跳 clock=888,308ms
12:35 ~ 12:44 约 9 分钟无读者（后台进程被外部回收，非设备断开）
12:44:10.6  计数器归零（由 host 时刻 − clock 反推）
预测回绕点  12:44:09.39（= 12:20:17.72 + 1,431.655765s）
偏差        +1.2 s          ← 比此前 8 次（≤12ms）大两个量级
HID 实例路径 9&2ff21532&0&0000 未变 → 没有重新枚举 / 没有拔插
```

排除频率漂移：同一时期 `tools/measure_tick.py`（658 s / 330 点最小二乘）测得
`Δ设备/Δ主机 = 1.0000101`（**+10 ppm**，tick = 3.00003 MHz），物理周期 1,431.641 s。
1.2 s 相当于 838 ppm，与实测相差 80 倍 → **不可能来自时基误差**。

结论：该次归零**不是回绕**，而是计数器被非回绕事件重置（最可能是长时间无读者时挂起/恢复，
固件重起报告定时器）。由此得到一个可用的判别器：

> 归零点偏离 `1,431,655.765` 超过约 1 s → 判「重置」；落在 `1,431,65x` → 判「回绕」。

## 第 8 次（13:08:02）—— 以重置后的新零点为基准，再次精确命中

```
13:08:02  [WRAP] 回绕前最后读数 = 1,431,651 ms
          理论 2^32@3MHz      = 1,431,655.8 ms
          偏差                = -4.8 ms
          回绕后首帧          = 1 ms
```

预测值由**重置后的零点**（12:44:10.62）+ 1,431.655765 s 推得 = 13:08:02.28，
实测 13:08:02.28（30 s 心跳与 250 Hz 捕获一致）。→ 周期本身准确，问题只在零点会被重置。

**这改变了「可预测」的含义**：回绕周期可预测，但绝对时刻只在「持续有读者、未挂起」的
epoch 链内成立。实现必须以 `clock <= prevClock` 为准，不能用墙钟外推。


## 对 12:44 那次「+1.2 s 异常」的判定实验（14:25）

三个候选原因，逐一做了实验：

| 候选 | 实验 | 结果 |
|---|---|---|
| **H1 主机壁钟被 NTP 缓调** | 60 分钟心跳里累计「Δ壁钟 − Δ设备」 | **基本排除**：累计仅 **+147 ms / 3600 s（≈40 ppm）**，无 `系统时间被修改` 事件，无单次 >100 ms 跳变 |
| **H2 无读者导致计数器重置** | 关闭句柄、**300 秒完全不读不打开**，再读 | **排除**：设备走过 `(1,431,655.765 − 1,430,049) + 298,472 = 300,078.8 ms`，实测 300,082 ms，**差 +3.2 ms**，且期间正常回绕、无空档 |
| **H3 读到陈旧缓冲帧** | 同 H2 的第二次读取（空闲 300 s 后的首帧） | **排除**：读到的帧比主机时刻新 3 ms 以内，Windows 不返回陈旧报告 |

**剩余解释**：12:44:09.4 的回绕**按计划发生了**（只是因为断档没有被采样到），
随后 `~12:44:10.6` 又发生了一次**独立的软重置**，把计数器重新归零。
两者相差 1.2 s 是巧合，不是周期误差——后续 13:08:02 与 14:20 两次回绕都以新零点为基准精确命中。

**方法论插曲（值得记）**：上面这个 300 秒测试的第一版脚本用 `Δ设备 < Δ壁钟 × 0.5` 判断「是否重置」，
因为窗口内恰好发生回绕（Δ = −1,131,577 ms），直接误判成「重置成立」。
**这正是本项目一直在警告的那类错误**——把无符号回绕当成负数。修正后才得到上面的结论。
