## 1. 边界与开放问题

### 1.1 覆盖到协议栈的哪一层

```
L0  报告字节格式与字段语义        ← 主战场（29 字节尾部已全部解析）
L1  报告时序 / 硬件时基           ← 已触及（3 MHz / 2³² 溢出，预测命中）
L2  命令-响应协议（bulk iface1）   ← 已解码序列，但未在用户态实现（需 WinUSB 绑定）
L3  SPI flash（校准/序列号）       ← 未触及，需写设备
L4  固件 / OTA                    ← 未触及，需写且不可逆
```

**如果你有写权限，请直接走 `0x09`**（有 0–9 电量档位、NFC）。**IMU 不用**——`0x05` 自带。
本文所有电量结论都是**"不能写"约束下的替代解**。

### 1.2 已解决

| 问题 | 结论 |
|---|---|
| 长跑掉帧暴涨 | 1432 s 时钟回绕，不是丢包（[Protocol §1.2](protocol.md)） |
| 只读怎么判满电 | 只有 `0x20`；占空比只能判"维持程度"（[Implementation §1.1](implementation.md)） |
| 读数能不能当电压 | 不行（[Gauge §1.1](gauge.md)） |
| `0x3C` 是什么 | 完成前瞬态，稳定 10.0 秒（[Charging §1.2](charging.md)） |
| 斩波维持会不会自己结束 | **会**，8h46m 后自行收尾（[Charging §1.2](charging.md)） |
| 恢复供电会不会立刻充电 | 取决于亏电（[Charging §1.5](charging.md)） |
| 高负载会不会影响充电决策 | 不会，且维持期不掉电（[Charging §1.6](charging.md)） |
| `0x23+` 那 29 字节到底是什么 | 微秒时间戳 + 温度 + **六轴 IMU**（[Protocol §1.4](protocol.md)、[IMU 专题](discovery-imu.md)） |
| 为什么打开设备却读不到任何帧 | 需主机**激活一次**；激活后脱离软件仍持续（[Protocol §1.5](protocol.md)） |
| 要 IMU 是不是必须写设备 | **不必**，`0x05` 自带完整六轴（[IMU 专题](discovery-imu.md)） |

### 1.3 尚未解决

| 8 | 回充阈值（读数掉到多少重新充） | 继续挂着直到触发。**已排除负载因素**：Apex 47% 按键 + 持续震动、读数降到 3,550 仍未触发（[Charging §1.7](charging.md)） |
| 9 | 摇杆满偏半径是否跨设备恒定（左 1,765 / 右 1,810 是个体差异还是通用值） | 第二台 Pro 2 跑 `tools/stick_range.py` |

| 11 | 激活命令的 **report ID** 未解出 | USBPcap 1.5.4 **不记录 SETUP 阶段**，而 report ID 在 `wValue` 里；需 Bus Hound 或更新的 USBPcap |
| 12 | 能否在用户态自己完成激活 | 需要 WinUSB 绑定 `MI_01`（Zadig/libusb），属装驱动，超出本仓库边界；已实测 HID 层三条路全部失败（见 [`tools/write/`](../tools/write/)） |
| 13 | IMU 芯片型号与安装偏角 | datasheet + 夹具；手测只能到 0.03°–3° 的放置误差，分不开 |

> 第 3 条性价比最高：几十块的功率计就能把"斩波 = 电流通断"从相关升级为直接测量，
> 同时给出读数的电压标度，且完全不违反只读原则。

### 1.4 引用要求

引用时请连同 **固件版本 + 拓扑 + `data/sw2_charge.csv`** 一起引用，不要只引结论。

## 2. 前人工作（prior art）

公开资料里已有三拨人在做这块，但**采集时程**决定了他们看不到本文的几条结论：

| 社区 | 代表工作 | 典型时程 | 能看见 1432 s 回绕吗 |
|---|---|---|---|
| 协议逆向 | dekuNukem（初代）、ndeadly（字段表）、kennethreitz（初始化） | 秒级到分钟级 | **不会**（其 USB 样本仅 499 次报告跳变 ≈2 s） |
| 内核驱动 | `hid-nintendo`；Linux 7.4 合入的 Switch 2 初始驱动 | 长期运行，但时间戳取自主机 `ktime` | **不会**（设备毫秒字段不参与时基） |
| 设备仿真 | HIDMaestro（标注固件 **1.1.5**）、SDL/Steam 侧 | 8 秒级冒烟 | **不会**（只需每 4 ms 发一帧） |

**检索状态（2026-10-24）**：以 `1,431,655` / `1431655` / "0x05 clock wrap" 等组合检索，
**未找到任何公开来源讨论该回绕或该常数**。因此本仓库一律写「**未检索到前人记录**」，
**不写「首次发现」**——后者不可证伪，也不该由作者自己断言。

**一处待核对的公开说法**：`switch2bridge-macos` 记「byte-0 counter 每报告 +1」。
若指 USB 上的 `0x05`，则与本文「前 4 字节是毫秒时钟、每帧 +4」冲突；
推测对方统计的是 BLE 侧 `0x09` 的 8 bit 计数器，但**未与作者核对**，列为开放项。

### 2.1 为什么「未检索到」不等于「全网第一」

上面那句「未检索到前人记录」容易被读成「我们是第一个」。**这两件事的差距很大**，
而且差距不是靠更努力的检索能填补的。有四类记录结构性地落在公开检索之外：

| # | 为什么检索不到 | 是不是能给结论 |
|---|---|---|
| 1 | **NDA 下的内部工作**：量产前 DevKit 已分发给游戏厂商与外设合作方，协议解析大概率早就做过，但受保密协议约束不会公开 | 结构性的，永远补不上 |
| 2 | **私有社群**：Discord / Telegram / 小众论坛里的主板与协议讨论不进搜索引擎，时间线上完全可能早于任何公开仓库 | 结构性的，永远补不上 |
| 3 | **命名与 PID 差异**：同一份分析可能挂着别的仓库名、以某个 Issue / PR 的形式存在（`hid-nintendo`、SDL、Joy-Con 逆向的分支），工程样机还可能用**不同 PID**，按 `057E:2069` 检索会直接漏掉 | 方法性的，可以改进但不保证 |
| 4 | **我们自己检索的边界**：2026-10-24 一次检索，以英文与中文为主，关键词围绕 `1,431,655` / `0x05` / `clock wrap` 展开。日文博客、非索引论坛、以及用完全不同措辞（例如只写"手柄电量"）的记录都在视野外 | **这一条是我们的短板，必须承认** |

前两类无法证伪，所以**不能作为证据**，只能作为「不要下断言」的理由；
第三类是可以改进的检索方法；第四类是我们自己的局限。

**所以政策不变**：全仓库一律写「**未检索到前人记录**」，不写「首次发现」。
这不是客气话——「第一个」这个标签的收益接近于零，代价却是实打实的：
它把一个可证伪的事实主张绑在了整篇文档上，而别人只要举出一个反例，
读起来就像整篇都不可信。真正值得被引用的是方法、数据和可复现性，不是时间戳。

> 如果你知道更早的公开记录，请开 issue。**指出我们错了，比确认我们对了更有价值**——
> 那会让这份文档变准确，而前者只让它变好看。

### 2.2 致谢

报告 ID 与字段偏移由 `ndeadly`、`kennethreitz`、`darthcloud/BlueRetro #1249` 的公开逆向奠基；
时钟回绕、状态位域、完整充电周期、读数锯齿、IMU 六面标定为本仓库独立实测得出。

**依赖的边界在哪一层，说清楚比较省事**：我们从前人那里拿的只有「字段在哪」——
`0x05` 是 64 字节、按键在 `[5..8]`、摇杆在 `[11..16]`、电量在 `[0x20]`、状态在 `[0x22]`。
这些不去重新猜，直接照字段表用。

但**这些字段随时间怎么变**，前人文档基本没写，全部来自本仓库的长时间观测：
23.86 分钟的时钟回绕常数、状态字节的位域语义、充电结束后的 2.9 Hz 斩波维持、
读数不是电压、摇杆只用掉 86% 量程、尾部 29 字节是时间戳 + 温度 + 六轴。
**换句话说：结构是继承的，行为是实测的。** 这个区分决定了这篇报告该被怎么引用。

**回馈**：`hid_reports.md` 把 IMU 轴方向与符号标为「需实测确定」，我们补上后提交为
[`ndeadly/switch2_controller_research` issue #2](https://github.com/ndeadly/switch2_controller_research/issues/2)，
附六面原始数据。激活命令序列的解读同样来自该仓库的 `commands.md`——
我们只做了独立验证（抓包 + 逐条对照），没有重新发明。

### 2.3 BLE 侧的实现：与本仓库互补，并且可以互相验证

[`LeonChrome/XinHeLianSheng-Pro2-Bridge`](https://github.com/LeonChrome/XinHeLianSheng-Pro2-Bridge)
（C# / Apache-2.0，2026-05 起，~78 stars）做的是**另一半**：把 Pro2 手柄通过 **BLE** 接到 Windows，
再以虚拟 USB 手柄（Pro1 / Xbox / PS5）交给游戏。本仓库走的是 **USB 只读观测**，两者不重叠。

> **对照的是哪一份代码，必须先说清。** 该项目当前发布的是纯软件 v2.0（Windows + VIIPER 后端），
> 而作者在 `source/` 的 README 里明确写了：`firmware/`、`pico/`、三合一相关目录**仅作历史参考**。
> 下面读的 `firmware/esp32s3_switch2_bridge/main/bridge/report_mapper.c` 属于那个**已归档的
> ESP32 固件（V5.9 时代）**，不是 v2.0 在跑的代码。
>
> 仍然值得对照，因为那份固件是**作者自己从 BLE 上解出来的**，与我们的 USB 侧测量互不相干；
> 但把它当成"对方当前实现"就会得出错误结论——我们在准备给该项目提建议时正是这么错过一次（见下方"摇杆"条）。

**四处独立吻合**（对照对象：上述已归档的 ESP32 固件；对方并未引用我们，其起始时间也早于本仓库）：

| 项目 | 对方实现 | 本仓库实测 |
|---|---|---|
| 报告布局 | 按钮 `5/6/7/8`、左摇杆 `11..13`、右摇杆 `14..16` | 完全一致（[Protocol §1.1](protocol.md)） |
| IMU 样本 | 12 字节：accel 在前 `+0/+2/+4`、gyro 在后 `+6/+8/+10`，int16 LE | 完全一致（`0x31`–`0x3C`） |
| 时间戳 | 4 字节 LE，**单位微秒** | 完全一致（`0x2B`–`0x2E`） |
| 按钮位序 | `fd2` 位图里 `C=0x4000`、`GR` 在 `GL` 之前、跳过 SL/SR 四位 | 与 §2.2 位域表逐位一致 |

> **这条对我们有直接意义**：本仓库是**先独立测出来、后才发现该项目**的。
> 顺序很重要——它意味着一致的布局不是互相抄的，而是同一份硬件事实的两次测量。
> 同时也再次印证了 §2.1：我们不是第一个做这件事的，2026-05 就已经有人在处理同一份运动数据了。

**两处值得记下的细节**：

1. **摇杆归一化——这条已经作废，但过程值得记。** 归档固件的 `axis12_to_i8()` 用
   `(value − 2048) / 16` 再夹到 ±127，即假设满量程 `0..4095`；按本仓库实测（半径 1,765 / 1,810），
   推到底只到 **≈110/127** 即 **86%**（[Protocol §2](protocol.md) 讲的就是这个坑）。

   **我们曾准备把这条作为建议提给对方，查证后撤销了。** 原因是：v2.0 更新日志写着
   "修正 Pro1 摇杆校准范围，移除输出端额外的中心吸附，**保留手柄校准**"——那正是本文实测支持的做法，
   对方已经自己解决；而我引用的是作者标为"仅作历史参考"的归档代码。

   > 教训：给外部项目提建议前，先确认**那段代码是否还在发布路径上**。这个"是否"一次请求就能查到，
   > 而"如果不在发布路径上"这个假设已经写进草稿里却没去验证——草稿写了退路，人却停在那里。
2. **固件版本**：对方能显示固件版本（通过命令通道读设备信息）。这提示一件事——
   固件版本**不是读不到，而是只读 HID 通道读不到**；走激活通道（`MI_01`）发 `0x02` 子命令就能取。
   本仓库的 [`data/DEVICE.md`](../data/DEVICE.md) 因此只用 `bcdDevice = 0x0201` 作替代标识，
   措辞是"只读可得"，不是"唯一可得"。
