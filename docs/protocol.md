## 1. 帧格式、时钟与按键

### 1.1 帧格式

固定 64 字节，`buffer[0]` = 报告 ID `0x05`，其后 63 字节为 body；**250 Hz（4 ms/帧）**。

> **但「打开设备」不等于「开始收数据」。** 只 `open` 一个 HID 句柄，一帧都收不到；设备必须先被
> 主机侧**激活一次**。激活之后，即使发起激活的程序已经退出，流仍以 250 Hz 持续——见 §1.5。
> 这一条是 2026-10-25 才确认的，早期版本写「上电即流」是错的。

> ⚠️ 偏移按**含报告 ID 的 buffer** 计，比社区文档里的 body 偏移**大 1**。这里最容易错。

| 偏移 | 长度 | 类型 | 字段 | 说明 |
|---|---|---|---|---|
| `0` | 1 | u8 | Report ID | 恒 `0x05`，不等则整帧丢弃 |
| `1` | 4 | u32 **LE** | Session Clock | 链路毫秒计数，每帧 +4；**1432 s 回绕**（§1.2） |
| `5` | 4 | u8×4 | Buttons | 位域，见 §1.3 |
| `11` | 3 | 12bit×2 | Left Stick | `LX=b0\|((b1&0x0F)<<8)`；`LY=(b1>>4)\|(b2<<4)` |
| `14` | 3 | 12bit×2 | Right Stick | 同上；**静止中心 ≠ 2048**（实测最多偏 +117） |
| `0x20` | 2 | u16 **LE** | Gauge Reading | **无量纲电量计读数**（满电 ≈3670–3728，非电压） |
| `0x22` | 1 | u8 | Charge Status | 见 [Charging §1.1](charging.md) |
| `0x23+` | 29 | — | **尾部遥测**：时间戳 + 温度 + 六轴 IMU | 见 §1.4 |

### 1.2 时钟：250 Hz、回绕、以及"重置"的判别

- **语义**：该 USB 链路建立以来的毫秒数，跨插拔归零。
- **回绕常数**：`2³² ticks @ 3 MHz = 1,431,655.765 ms`（23.86 分钟）。
  不是任何 2ⁿ 毫秒（2³² ms = 49.7 天、2²¹ ms = 35 分钟，均不符）。
- **时基精度**：658 秒 / 330 点最小二乘 → `Δ设备/Δ主机 = 1.0000101`，**+10 ppm**，
  物理周期 1,431.641 s。晶振级，排除"周期漂移"。

**可预测性**：先由常数做出预测，再用 250 Hz 守到回绕点——

```
预测 1,431,655.765 ms
实测 1,431,650 / 1,431,652 / 1,431,651 …   偏差 −5.8 / −3.8 / −4.8 ms
整夜 22 次回绕，0 次重置
```

**但绝对时刻会漂**：epoch 零点可被非回绕事件重置。实测一次：计数器在 `12:44:10.6` 归零，
而预测点是 `12:44:09.39`（**+1.2 s**），同期时基已验证 ±10 ppm，故不可能来自频率误差。

**实现约束（强制）**：

1. 永远以 `clock <= prevClock` 判 epoch 边界，**不要**用"墙钟 + 周期"推算；
2. **严禁无符号直接相减**——数小时后会掉帧爆炸；
3. 判别器有**采样密度前提**：

```
逐帧（250 Hz）：  归零点偏离 1,431,65x > 1 s  →  重置
稀疏（30 s 心跳）：prev_clock + 采样间隔 ≥ 1,431,655.765  →  回绕落在间隙内（正常）
                                否则时钟却变小      →  真正的重置
```

> 本仓库的审计脚本曾用第一条去判 30 秒心跳，把正常回绕误判成重置。稀疏采样必须用第二条。

### 1.3 按键位域（1 = 按下）

| byte | 0x80 | 0x40 | 0x20 | 0x10 | 0x08 | 0x04 | 0x02 | 0x01 |
|---|---|---|---|---|---|---|---|---|
| `[5]` | ZR | R | SL-R | SR-R | A | B | X | Y |
| `[6]` | — | C | Capture | Home | LS | RS | Plus | Minus |
| `[7]` | ZL | L | SL-L | SR-L | Left | Right | Up | Down |
| `[8]` | — | — | — | Headset | — | — | GL | GR |

摇杆**不能按绝对值归一化**：静止中心实测 `(2040,2048)` / `(2127,2163)`。
准确标定需读 SPI 校准块（要写设备）。**UI 层请用原始 12bit + 死区，不要声称"已校准"。**
摇杆实际能用多少量程，见下节 §2。

### 1.4 尾部 29 字节：时间戳、温度、六轴 IMU

这 29 字节曾被标为「未解析／建议忽略」。2026-10-25 用**静止 / 晃动 A/B** 加**六面标定**
全部定性，一个不剩：

| 偏移 | 长度 | 类型 | 字段 | 换算 / 说明 |
|---|---|---|---|---|
| `0x23`~`0x29` | 7 | u8 | 保留 | 恒 `0x00` |
| `0x2A` | 1 | u8 | 标志位 | 恒 `0x01`，含义未知 |
| `0x2B` | 4 | u32 **LE** | Timestamp | **微秒**；与主机时钟独立，每帧 +3750 或 +5000 |
| `0x2F` | 2 | int16 **LE** | Temperature | `T[°C] = 25 + raw / 126.9` |
| `0x31` | 12 | int16×6 **LE** | Accel X/Y/Z + Gyro X/Y/Z | 见下 |
| `0x3D`~`0x3F` | 3 | u8 | 保留 | 恒 `0x00` |

IMU 换算用**实测标定值**，不是标称值：

```
0x31:0x32  ax   a[g]   = (raw - 10.5)  / 4090.8
0x33:0x34  ay   a[g]   = (raw +  5.2)  / 4090.7
0x35:0x36  az   a[g]   = (raw - 102.3) / 4096.3     ← 正面法线
0x37:0x38  gx   w[dps] = (raw - 8)     / 16.384
0x39:0x3A  gy   w[dps] = (raw - 3)     / 16.384
0x3B:0x3C  gz   w[dps] = (raw - 7)     / 16.384

量程：加速度 ±8 g       陀螺 ±2000 dps
零偏：**必须减**。不减的话 gx 会以 0.49 dps ≈ **29.7 °/分钟** 累积漂移（三轴 29.7 / 12.1 / 23.7）
坐标系：右手系；Z = 正面法线（平放朝上读 +1 g）；Y 沿长轴、指向 USB 口
```

**结论：`0x05` 是一份完整的六轴遥测帧**——按键、摇杆、电量、时间戳、温度、IMU 全在同一帧里，
只读轮询即可全部拿到，不需要 `0x09`。

> 判定依据、六面标定过程、以及这批数据为什么一度被作废又恢复，见
> [`discovery-imu.md`](discovery-imu.md)。
> 轴方向与符号这一项，上游 `hid_reports.md` 标注为「需实测」，我们的结果已提交至
> `ndeadly/switch2_controller_research`（issue #2）供交叉核对。

### 1.5 激活：为什么「打开设备」还不够

只 `open` 设备再 `read`，拿到的会是 **0 帧**。不是丢包、不是速率协商，是设备根本没开始发。

| 观察 | 结果 |
|---|---|
| 未激活时枚举 | 正常：Windows 认作游戏控制器，PnP 全部正常 |
| 未激活时 `read` | **0 帧**，任何报告 ID 都没有 |
| 未激活时按键 | 不唤醒，仍然 0 帧 |
| 被主机激活后 | **直接 250 Hz**，无爬坡、无过渡态 |
| 激活后关掉发起激活的软件 | **流不中断**（实测 Steam 全退出后仍 250.2 Hz） |
| 拔线重插 | 退回未激活状态，需重新激活 |

所以激活是**一次性开关**，不是持续协商。命令走 `MI_01` vendor 接口，**不是** HID 接口 `MI_00`——
这也是为什么在 HID 层发什么都进不去。命令序列与语义见
[`discovery-imu.md` §8.1](discovery-imu.md)。

> **对本仓库的约束**：所有数据都采自「已被激活」的设备，激活由外部软件（实测为 Steam）完成，
> 本仓库探针只读取。
> 这不是缺陷，而是一个**必须写明的实验前提**——否则照着复现的人会得到 0 帧，然后以为设备或代码坏了。

**实测的激活手段就是 Steam，而且不需要登录：**

| 步骤 | 结果 |
|---|---|
| Steam 完全退出 + 拔插手柄 | **0 帧** |
| 启动 Steam，**停在登录界面、不登录** | 手柄被接管（绿灯亮），**数据立即 250 Hz** |
| 关掉 Steam | 流不中断，仍 250.2 Hz |

「登录界面就能接管」这一条把范围缩小了一半：接管发生在登录**之前**，所以驱动它的是
Steam 客户端的**本地 HID / 控制器服务**，与账号层的 Steam Input 配置无关。

同时也要说清**没测过什么**，别让这条读成"只有 Steam 能激活"：

- **未测**：其他软件（SDL 游戏、`HIDMaestro`、Linux `hid-nintendo`）能否激活。上游资料指出
  SDL 的 Switch 2 驱动也在 `iface1` 上发启动命令，所以"唯一激活者"是过度断言；
- **未测**：在 Steam 设置里关闭「控制器支持 / Steam Input」后，是否仍然会接管。
  **当前 Steam 版本里没找到这个开关**（可能已移除，或按设备隐藏），所以这条暂时无法验证；
- **未测**：不同 Steam 版本的行为是否一致。**可复现性的天花板就在这里**——激活那一步挂在
  一个会自更新的第三方客户端上。

## 2. 摇杆：行程实测与量程（12 bit 解包验证）

Apex 靶场是首次让摇杆离开中心（此前所有数据都在 2040~2168 徘徊）：

| 轴 | 实测范围 | 跨度 | 中点 |
|---|---|---|---|
| LX | 390 ~ 3,719 | 3,329 | 2,054 |
| LY | 563 ~ 3,582 | 3,019 | 2,072 |
| RX | 568 ~ 3,722 | 3,154 | 2,145 |
| RY | 616 ~ 3,797 | 3,181 | 2,206 |

- **正面结论**：在 390~3,800 这么宽的行程内，数值**连续、无跳变、左右对称、四轴互不干扰**
  → §1.1 的 12 bit 解包（`x = b0 | ((b1 & 0x0F) << 8)`、`y = (b1 >> 4) | (b2 << 4)`）**验证正确**。
- **但从未触及 0 / 4,095**。为区分"硬件限位"与"游戏死区"，随后在**裸 HID（无游戏运行）**
  下做了极限行程抓取（`tools/stick_range.py`，7,750 帧，静止中点 左(2061,2068) / 右(2159,2152)）：

| 轴 | 最小 | 最大 | 跨度 |
|---|---|---|---|
| 左 X | 431 | 3,780 | 3,349 |
| 左 Y | 571 | 3,581 | 3,010 |
| 右 X | 558 | 3,674 | 3,116 |
| 右 Y | 386 | 3,762 | 3,376 |

  **最大偏转半径**（相对实测中点）：左 **1,765**、右 **1,810** counts，
  即理论满偏 2,047 的 **86.2% / 88.4%**，**四轴无一触及端点**。

- **结论：这是真实的机械/固件限位，不是游戏死区。** 三条依据：
  1. 裸 HID 下（不经过任何游戏）推到物理极限仍然到不了端点；
  2. Apex 内实测范围（390~3,722）与裸 HID 极限（431~3,780）**几乎一致**，
     说明游戏并未压缩行程——那个"81.3%"就是硬件极限本身；
  3. 左右半径接近（1,765 vs 1,810，差 2.5%），符合**圆形轨迹 + 统一半径**的几何，
     而不是单轴死区造成的各向异性（左 Y 跨度仅 3,010，但合成半径仍 1,765）。

- **工程含义（重要）**：**归一化绝不能假设 0~4,095 或 ±2,048**。
  若按满量程映射，用户把摇杆推到底也只得到 **0.86**，表现为"永远推不满 / 转视角慢半拍"。
  正确做法是先标定实测**半径**（本项目 1,770~1,810，左右可不同），
  或用 SPI 校准块（需写设备，超出只读边界）。
  **用半径而非单轴跨度做归一化**：单轴行程受机械公差影响（左 X 3,349 vs 左 Y 3,010），
  半径才是摇杆的真实可达距离。

### 2.1 Steam / SDL 对摇杆做了归一化（实测）

把左摇杆分三段推到底，同时记录原始值与 Steam「检测输入」页的显示值
（`data/stick_full_right_2026-10-25.csv`，静止中心 `LX=2065`）：

| 原始行程（LX−2065） | Steam 显示 | 每计数 |
|---|---|---|
| 435 | ~10000 | 23.0 |
| 944 | ~20000 | 21.2 |
| 1605（推到底） | **32767（满）** | 20.4 |

**×16 线性映射被排除**：若按 `(raw−2048)×16`，三点应显示 7232 / 15376 / 25952，
与实测差得远。**归一化假设成立**：Steam 把「推到底」直接映射到满量程，
反推它认为的满偏行程 ≈ **1696** 计数——与本仓库实测的 1605（本次）/ 1719（此前）吻合。

**这条改变了 §2 结论的适用范围：**

| 谁 | 推到底得到 |
|---|---|
| 直接读 `0x05` 原始 12 位 | **0.86**（本仓库的警告针对这一类） |
| 经 Steam Input / SDL 读取 | **1.00**（归一化到实测满偏） |

所以「永远推不满」只在**自己解原始字节**时出现；走 Steam 的人碰不到。
此前文档没写这一层，容易让读者以为 0.86 是普适的。

> **关于 Steam 默认死区 8192**：如果那一页显示的是死区**后**的值，行程 27%（435/1605）
> 再扣 25%（8192/32767）只剩 2.8%，应显示约 900——实测是 10000，约等于 27% 的满量程。
> 也就是说**这一页显示的是死区前的值**，死区无法从这里验证，仍是开放项。

## 3. 主机侧视角：SDL / Steam 的映射串能读出什么

Steam 的「控制器布局」界面可以复制出一段 SDL 映射串（来自 Steam 用户 2026-10-25 实测）。它不是文档，
但是一份**机器可读的、由驱动作者写下的断言**，可以用来交叉验证我们对位域的理解。

### 3.1 GUID 的结构：不止 VID/PID

```
030056fb7e0500006920000001026800
```

| 字节 | 值 | 含义 |
|---|---|---|
| `[0:2]` | `03 00` | bus = **0x0003 = USB**（蓝牙会是 0x0005） |
| `[2:4]` | `56 fb` | 设备名的 CRC16 = `0xfb56`（与串尾 `crc:fb56` 自洽） |
| `[4:6]` | `7e 05` | vendor = **0x057E** |
| `[6:8]` | `00 00` | — |
| `[8:10]` | `69 20` | product = **0x2069** |
| `[10:12]` | `00 00` | — |
| `[12:14]` | `01 02` | **version = 0x0201** |
| `[14]` | `68` | 驱动签名 `'h'`（HIDAPI） |
| `[15]` | `00` | 驱动数据 |

`[12:14]` 的 `0x0201` 不是随机值：用 `hid.enumerate()` 读同一设备的 `release_number`，
得到 **0x0201**（USB 描述符里的 `bcdDevice`）。两条独立路径一致。

> **实用价值**：`bcdDevice` 是**只读可得的版本标识**（`hid.enumerate()` 的 `release_number` 字段），
> 不需要发任何命令。它不等于 Switch 界面里那个「手柄固件版本」字符串，
> 但可以拿来判"两台设备是不是同一版"。记录见 [`../data/DEVICE.md`](../data/DEVICE.md)。

**确定性**：同一设备两次导出（2026-10-25，间隔约 6 分钟）**逐字节一致**——374 字节、30 个字段。

但要注意它**为什么**一致：**SDL 对输出做了规范化**，不是设备上报顺序稳定。
20 个标准键严格按名字字母序排列（`a, b, back, dpdown, …, x, y`），
`misc1/misc2/paddle1/paddle2` 这 4 个扩展键追加在尾部。

所以这条串可以当**设备指纹**用（Steam 的控制器布局正是按 GUID 索引的，换台电脑仍命中同一份配置），
也可以当**回归测试的期望值**（驱动一改、串就变）。
但**不能**反过来用它推断"设备行为很稳定"——那要看帧数据，不是看这行字符串。

### 3.2 按钮对照：哪些对上了，哪些对不上

| SDL 映射 | SDL 叫法 | 我们的位域 | 备注 |
|---|---|---|---|
| `a:b0` `b:b1` `x:b2` `y:b3` | 面键 | `[5]` 0x08/0x04/0x02/0x01 | ✓ 四个都在 |
| `leftshoulder:b9` `rightshoulder:b10` | L / R | `[7]` 0x40 / `[5]` 0x40 | ✓ |
| `lefttrigger:a4` `righttrigger:a5` | **ZL / ZR** | `[7]` 0x80 / `[5]` 0x80 | ⚠ **SDL 把它们当轴，不是按键** |
| `back:b4` `start:b6` | **− / +** | `[6]` 0x01 / 0x02 | ⚠ SDL 的 back = 减号，不是 Capture |
| `guide:b5` | Home | `[6]` 0x10 | ✓ |
| `leftstick:b7` `rightstick:b8` | 摇杆按下 | `[6]` 0x08 / 0x04 | ✓ |
| `paddle1:b13` `paddle2:b14` | **背键** | `[8]` 0x02 / 0x01 = **GL / GR** | ✓ 独立印证这两个键存在且可用 |
| `misc1:b11` `misc2:b12` | 未命名 | 候选：`[6]` 0x40(C)、`[6]` 0x20(Capture)、`[8]` 0x10(Headset) | ⚠ **未测**，需逐个按 |
| `dpup:h0.1` `dpdown:h0.4` `dpleft:h0.8` `dpright:h0.2` | 十字键 | `[7]` 0x02/0x01/0x08/0x04 | 顺序不同，驱动做了重排 |

**三个容易踩的坑：**

1. **ZL / ZR 是轴不是键**。取值 `a4`/`a5`，说明 SDL 把它们当模拟量。我们的 `0x05` 位域里它们是
   两个 bit（0x80），所以**推测**是驱动把数字量合成 0 / 满两档——未验证。
2. **`back` 是减号，不是 Capture**。按 SDL 惯例 `back` 通常指 Select/View，这里对应 `−`。
3. **`SL` / `SR`（导轨键）没有被映射**。它们在我们位域里占 4 个 bit（`[5]`/`[7]` 的 0x20/0x10），
   但在 Pro 手柄形态下 SDL 直接忽略——说明那几个 bit 只在滑轨/分体场景有意义。

另外 `hint:!SDL_GAMECONTROLLER_USE_BUTTON_LABELS:=1` 是任天堂特有的**按键标签反转**处理：
物理上"下排右边"那个键印着 A，但位置语义是"确认键在右"。这个 hint 让 SDL 按**位置**而非印字映射。

### 3.3 这张表**没有**的东西

映射串只描述按键/轴，**不含陀螺仪与加速度计**——SDL 的传感器走独立 API，不出现在这串里。

所以它不能替代 `0x05` 的 IMU 字段（§1.4）：想做体感，还是得自己解 `0x31`–`0x3C`。
