## 1. 实现规范

### 1.1 状态分类器

主信号是**窗口占空比**（0/1 统计，稳定），趋势只作辅助（读数抖动跨度 > 快充信号）。

> **术语约定**：下文的 `duty00` 指 **`0x00`（断开/不充电）的时间占比**，与电子工程惯例的
> "duty cycle = ON 导通占比"**相反**。82%~90% 的数值是 `duty00`（OFF 占比）；对应的 ON 导通
> 占空比是 18%~10%。别把两者混为一谈。

```
enum State { Discharging, FastCharging, ToppingOff, Full, GenericCharging }
const KNOWN = { 0x00, 0x24, 0x2C, 0x34, 0x3C };   // 0x20 单独处理
const FULL  = 0x20

feed(raw, status, t):
    # 0x20（完成）不进占空比窗口，直接返回。原因见下。
    if status == FULL:        return Full
    if status not in KNOWN:   return GenericCharging   # 未知字节降级，UI 标 Raw
    push(t, raw, status);  drop_older_than(t - 600)
    if 窗口覆盖 < 60 s:       return current
    duty00 = fraction(status == 0x00, 最近 120 s)
    delta  = median(导通采样后窗) - median(导通采样前窗)
    if duty00 >= 0.15:        return ToppingOff        # 0.15~1.0 都只是"维持程度"，无需再细分
    # 走到这里：>85% 时间在充电族(0x34/0x2C/0x24)，即真的在充电
    if delta  <= -8:          return Discharging       # 充电态读数却下行 → 异常/可疑
    return FastCharging
```

三点说明：

- **`0x20` 必须提前返回、不进窗口**。若把 `0x20` 也 push 进窗口，它停留数小时后会把窗口里的
  `0x00`/导通样本全部稀释，一旦跳回充电态，`duty00` 和 `delta` 都会严重失真。
  代价是 `0x20 → 其他状态` 后要重新攒满 60 秒窗口——在 8 小时周期里可忽略。
- **`duty00` 只设一个 `0.15` 阈值**。曾有两个阈值（0.75 / 0.15）但都返回 `ToppingOff`，
  上一行是死分支。实测占空比到 90% 仍维持数小时，之后又做一轮真充——**占空比只度量
  "不充电的时间占比"（= 还需要充多少），不是"已满"**。只有 `0x20` 能判满。
- **`Discharging` 在本只读 USB 通道下几乎不可达**：USB 连接时要么在充电族，要么是 `0x20`
  （已完成、已提前返回），不存在"真正用电池放电"的状态字节。它保留是三个原因：
  ① 防御未知固件；② 为未来接 BLE 通道预留；③ `delta <= -8` 且低占空比意味着"充电态却读数下行"，
  本身值得单独标记（可能接触不良 / 供电不足）。
  **已知误触风险**：边充边玩 + 震动时，瞬时压降可能让 `delta` 短暂 `<= -8` 而误报。
  生产实现应加"持续 ≥30 秒才确认"的滞回，或直接用谷值深度区分震动（见 Charging §1.7）。

### 1.2 七条防御（逐条落地）

1. **`0x20` = 完成**：`status==0x20` 无条件 `Full`。`0x3C` 必须进已知集合（否则每轮充满前报 10 秒未知）。
2. **未知字节降级**：集合外字节**不抛异常、不判离线**，置 `GenericCharging` 并标注 `Raw: 0xNN`。
3. **读数上下溢**：若 UI 需要"相对进度条"，用**经验线性映射**（`[3520, 3720]` → `[0,100]`），
   一律 `Clamp(p,0,100)`。⚠️ 上限用实测满电 **3720~3728**，不要用旧的 3680；
   且这是**纯粹的经验映射、不是真实 SoC**（读数不是电压，见 [Gauge §1.1](gauge.md)），
   只在"电池供电 + 非震动"下有意义。
4. **回绕防护**：`cur < last && last-cur > 1000` → 自增 epoch、重置基准；禁止无符号直接相减。
   稀疏采样时改用 [Protocol §1.2](protocol.md) 的间隙感知判据。
5. **链路防抖**：单次读异常/超时维持 1~2 s 重试，**连续 3 次失败**才判 `Offline` 并释放句柄。
6. **禁止瞬时值驱动 UI**：`0x24` 只占 10~12%，1 Hz 轮询会每 8 秒闪一次"充电中"；
   必须用窗口占空比。同理，读数值必须平滑（[Gauge §1.2](gauge.md)）。
7. **震动时冻结电量读数**：窗口内读数极差（谷值深度）> 15 → 判定 `RumbleActive`，
   冻结"进度/电量"读数更新（或只取窗口 P90 上包络线）。否则玩家一开枪，
   电池供电下的瞬时压降（[Charging §1.7](charging.md)，谷深 24~37）会让 UI 电量**瞬间暴跌 20%**。

### 1.3 单测夹具（真实帧）

05 9B 22 00 00 …                      → clock=8859（0x229B）
05 9F 22 00 00 …                      → clock=8863（下一帧，+4）
05 42 AD 00 00 … … D3 0D …            → clock=44354, gauge=3539, status=0x2C

05 01 00 00 00 …                      → clock=1（新 epoch 首帧）

### 1.4 摇杆的动态圆心与半径校准（纯只读）

不读 SPI 校准块的前提下，用**运行时统计**消掉单台设备的中心偏移：

```
# 锁定初始圆心（带守卫，防止"推着摇杆启动"把偏移值当圆心）
cx, cy = 2048, 2048        # 兜底值：先按理想中心，直到抓到静止窗口
buf = []
for each frame:
    if 该帧无按键(btn == 0):
        buf.append((x, y))
    else:
        buf.clear()          # 有输入就清空，重新攒静止窗口
    if len(buf) == 50:       # 50 帧 = 200 ms
        if max(x)-min(x) < 10 and max(y)-min(y) < 10 \
           and 1800 <= mean(x) <= 2300 and 1800 <= mean(y) <= 2300:
            cx, cy = mean(x), mean(y)    # 满足静止 + 先验中心窗，锁定
            break
        else:
            buf.pop(0)        # 不满足，滑窗继续，绝不硬取
# 锁定后：
运行中维护最大偏转半径 r_max（每帧 hypot(x-cx, y-cy) 的滑动最大值）
归一化用 r = min(r_max, 1780)     # 1780 = 实测半径下界，防启动初期 r_max 偏小
出轴 = clamp((x - cx) / r, -1, 1)
```

- **"无操作样本"的判据**：必须同时满足「连续 50 帧极差 < 10（真静止）」+「均值落在
  [1800, 2300] 的先验安全窗内」。否则用户边推摇杆边插线 / 启动的 200 ms 内恰好在推，
  会把推到底的坐标（如 3,700）当成圆心，后续整个会话的摇杆彻底废掉。
- **为什么用运行时圆心**：右摇杆静止中心实测偏到 `(2159,2152)`（偏离理想 2048 达 +117），
  按固定 2048 做中心会让"没推"输出一个永久偏移。抓到静止窗口后即可消掉。
- **为什么半径取 `min(r_max, 1780)`**：硬件半径实测 1765~1810（[Protocol §2](protocol.md)）。
  启动初期 `r_max` 还没被推满，若直接用会高估出轴值；用 1780 做上限兜底。
  玩家推到更大半径时 `r_max` 会追上去，因此不会"推不满"。
- 这套只是**近似**，不如 SPI 校准块精确，但对"旁路 UI / 输入映射"已经够用，并且全程不写设备。
