## 2. Established today (ordered by evidence strength)

### 2.1 Strongest: the wrap is 2³² ticks @ 3 MHz

```
predicted     1,431,655.765 ms
observed      1,431,650 / 1,431,652 / 1,431,651 …   (error −5.8 / −3.8 / −4.8 ms)
time-base fit 658 s / 330 points → +10 ppm (3.00003 MHz), physical period 1,431.641 s
```

The only conclusion of the day that was **predicted first, verified afterwards, and repeated**.
It also yields a usable discriminator:

> A zero-point deviating from `1,431,65x` by more than ~1 s → a **reset**; landing in that band → a **wrap**.

**On the +1.2 s anomalous zeroing at 12:44** (the "three hypotheses eliminated" from the timeline) —
the three hypotheses that were ruled out:

1. **Time-base frequency drift**: a 1.2 s slip needs ~838 ppm of drift, but `measure_tick.py`
   measured +10 ppm over the same period — 80× off, ruled out.
2. **No-reader reset of the firmware timer**: with the handle closed and 300 s of no reading at all,
   the counter still ran exactly 1:1 (error +3.2 ms) and wrapped once normally — "nobody reading
   resets it" is ruled out.
3. **A stale buffered frame**: the first frame after 300 s idle was within 3 ms of the host clock;
   Windows does not return stale reports.

Conclusion: the wrap at 12:44:09.4 **happened on schedule** (just unsampled during the gap), and a
**separate soft reset** occurred 1.2 s later. With all three hypotheses eliminated this is the only
self-consistent reading; why the soft reset happens is still unknown and left open.

### 2.2 The status byte is a bitfield, but "stage index" does not hold

| Bit | Meaning | Evidence |
|---|---|---|
| b5 `0x20` | external power present | set in every non-zero value, clear in `0x00` |
| b2 `0x04` | charging current flowing | set in `0x2C/0x24/0x34/0x3C`, clear in `0x20` |
| b4:b3 | **not** a monotonic stage | insertion sequence `0→2→1→2`, a clear counter-example |

### 2.3 `0x20` = charge complete, and **not** an absorbing state

- the red LED goes out at the same instant;
- it can persist for 5 h 39 m;
- **a replug exits it immediately** — no need to discharge to a threshold.

### 2.4 There are **two** post-charge forms

| Form | Behaviour | Observed |
|---|---|---|
| A | `0x20` static, reading decays slowly (−0.22/min) | 09:42–15:21, 5 h 39 m |
| B | `0x00`/`0x24` chopping at **2.9 Hz** | 15:23–21:45, 6 h+ |

**The trigger is unknown**, and the "B → A" transition **was never observed** on this day.
(Note: written during the day. The overnight appendix A already observed the chopping → `0x20` self-wrap-up, so this sentence is superseded.)

### 2.5 Chopping parameters

```
OFF segment (0x00, off / not charging)  284 ms (not a single millisecond of change in 6 hours)
ON segment (0x24, conducting)           52 → 40 → 32 ms (narrowing slowly)
0x00 off-duty (OFF-duty)                82 % → 90 % (rises very slowly, then stabilises)
ON duty                                 18 % → 10 %
frequency                               2.9 Hz
```

> **Terminology**: "`0x00` off-duty" (called `duty00` in code) is the **fraction of time not
> charging** — the *opposite* of the EE convention (duty cycle = ON fraction). Don't be confused by
> "ON narrows yet off-duty rises": OFF is constant at 284 ms while ON shrinks from 52 to 32 ms, so the
> OFF fraction = 284/(284+ON) rises from 84 % to 90 %, while ON duty falls from 16 % to 10 %.

### 2.6 The reading swings with the chopping, lagging 40–60 ms

60 s / 15,001 frames, bucketed by "k-th frame after a transition":

| k | → `0x24` | → `0x00` |
|---|---|---|
| 0 | 3,673 | **3,693** |
| 8 | 3,689 | 3,687 |
| 15 | **3,692** | 3,674 |

→ A single frame carries **±10** of chopping noise; always average over ≥1 period (350 ms).

### 2.7 Whether a replug starts real charging depends on **how depleted it is**

| Replug | Reading before | First frame | Real charging? |
|---|---|---|---|
| 15:21 | 3,616 (discharged) | `0x24` | yes (~1 min of `0x34`) |
| 18:00 | 3,676 (topped up) | `0x00` | **no** |

### 2.8 Load does not affect charging decisions, and maintenance draws no battery

39 minutes of real gameplay (button activity peak 51 %): zero status changes, reading range of only 4.
On battery, at −0.22/min it should have lost 8–9 units → **it is actually USB-powered**.
The reading difference between button-active and idle frames is **−0.35** (below resolution, not measurable).

## 4. Tool bugs fixed today (each one instructive)

| Bug | Symptom | Root cause |
|---|---|---|
| `dclk < dwall * 0.5` used to detect a reset | a normal wrap was judged "reset confirmed" | **treating an unsigned wrap as negative** — exactly the error this project keeps warning about |
| `if not wait_for(...)` | the device was already unplugged, yet the script reported a timeout | the success value *is* `None`; "not found" and "failed" look identical |
| `_pylibs` path over-ascended one level | `ModuleNotFoundError: hid` | the root was computed wrongly when the file lives in `tools/`; only a real run exposed it |
| `play_monitor` did not catch OSError | the process crashed on unplug with no `[Offline]` | only `KeyboardInterrupt` was caught |
| Writing regex inside a shell command | `\d` became `/d`, zero lines parsed | double-quote escaping; rule changed to **always put regexes in a .py file** |

> **On why the `-73 ms` skew in §1 has the opposite sign of the +10 ppm in §2.1**: they are not
> the same quantity. `+10 ppm` comes from `measure_tick.py` using a **monotonic clock**
> (`perf_counter`) — it is the device crystal's rate versus the host's monotonic clock. The `skew`
> comes from `log_status_transitions.py` accumulating `Δwall − Δdevice` over the **wall clock**
> (`time.time()`, which NTP can slew) — it reflects wall-clock drift, not the crystal. Opposite
> signs are expected; do not conflate them.

## Appendix A · Overnight addendum (10-24 21:36 → 10-25 06:41)

Same device, same link, left running for 9 h 05 m. This stretch resolved two open questions (#8, #9)
and revealed a **wrap-up pattern never seen before**.

### A.1 The wrap-up is not a fade-out, it is a reversal

Yesterday at 19:59 I extrapolated from "ON pulse 52→40→32 ms" to "pulse → zero → switches to `0x20`".
**The direction was completely wrong.**

| Time | Status composition | Reading |
|---|---|---|
| 22:30–23:45 | `0x00` 89–91 % (steady, already 7.5 h) | 3,677 |
| 23:48–23:55 | **churn**: `0x24 → 0x34(4 ms) → 0x2C(440 ms)`, **38 cycles** | 3,72x |
| 23:59–00:09 | **`0x34` full-power charging, ~10.5 min** | 3,728 |
| 00:09:35 | `0x34 → 0x3C` | 3,727 |
| 00:09:45 | `0x3C → 0x20` (enters form A) | 3,715 |
| 00:10–06:34 | `0x20` 100 %, monotonic decay | 3,708 → 3,603 |

Three hard conclusions:

1. **The chopping maintenance phase ends by itself**, no replug needed; ~**8 h 46 m** from entering maintenance to completion.
2. **The wrap-up path is `0x2C` → `0x34` (full power) → `0x3C` → `0x20`**, not a decaying pulse.
3. **`0x3C` duration = 10,004 ms** (n=2, both exactly 10 s) → parsers must tolerate this ~10 s window.

### A.2 A new form: churn

23:48–23:55, 38 cycles, each:

```
0x24 (~28 ms, current flowing)
  → 0x34 (typically 4 ms, exactly one frame)
  → 0x2C (median 440 ms)
  → back to 0x24
```

`0x34` exists for only **4 ms = one frame interval**, visible only at 250 Hz.
**Software polling at 1 Hz never sees this** — it only sees `0x00`/`0x24` and then suddenly `0x20`.

### A.4 Another defect of my own fixed

The audit script initially flagged 23:58 as a "reset", because the rule was "a zero-point more than
1 s away from 1,431,65x means a reset" — **but the heartbeat interval is 30 s, so the last frame may
legitimately be 30 s early**.

With the gap-aware rule: `prev + interval ≥ 1,431,655.765` → the wrap fell inside the gap (normal).
Re-audit result: **22/22 all wraps**, prediction vs observation differing by −294 to +710 ms
(whole-second timestamps plus 4 ms frame stepping).

> This is now in [`protocol.md` §1.2](protocol.en.md): **the discriminator assumes a sampling density**;
> sparse sampling must use the gap-aware version. This is the day's **6th tool/script bug**
> (the five in §4 plus this one). Note it is *not* the same as §4 bug #1 (`dclk < dwall*0.5`):
> that one was **unsigned-subtraction overflow**; this one is **timestamp-alignment lag under sparse
> sampling** — two independent defects that both happened to look like "a normal wrap misread as a reset".
